This release fixes short messages that were sometimes lost on their way to the session, which failed some transfers of large files at their start.

## What I saw

Two transfers failed the same way on 2026-11-09, and the logs of both sides show it.

- With 0.4.0, the client sent the drop, then 9 ms later the start of the transfer, then the start of the file and a large piece of data. The agent received the drop and the start of the file, never the start of the transfer.
- With 0.4.1 on both sides, the client sent the start of the transfer, then the start of the file, then 8 ms later the first piece of 174 868 characters. The agent received the start of the transfer and the piece, never the start of the file.

Nothing reported an error, on either side. Two other transfers of the same day, 18 MB and 496 MB, worked. Each time, a short message sent just before a large one disappeared between the Microsoft Remote Desktop control and the agent. The likely cause is that the control sends the text after the call returned, from memory that .NET frees as soon as the call returns.

## What changed

- The client allocates the text it hands to the control itself, and frees it only once the agent confirmed later data, or 10 seconds later for a message without data. The log says at the first connection of each tab whether this path is in use.
- The client sends its messages together: everything decided while the window handles one event leaves in one call, up to 200 000 characters, just above the largest call I saw work. The start of a transfer and the start of its first file now travel with the first data instead of alone in front of it. The limit is the new setting `transferBatchCharacters` in `%LOCALAPPDATA%\UltimateRDP\client.json`, from 50000 to 1048576; you should not need to change it.
- When the agent sees that a message never arrived, it says which one: "A message of the transfer was lost on the way: fileBegin for file 0 never arrived. Try again."
- The client has a `logLevel` setting in `%LOCALAPPDATA%\UltimateRDP\client.json`. With `debug`, its log has every message sent to the agent and every call to the control.

The transfer does not start again by itself after such a loss; drop the files again.

## Upgrade

Install 0.4.3 on both sides. The fix itself is in the client: a 0.4.1 or 0.4.2 agent works with the 0.4.3 client, it only describes a lost message as "Data was lost or damaged on the way." A 0.4.3 agent also works with an older client.

If a transfer still fails at its start, I would like both logs with `logLevel` set to `debug` on both sides.
