This release fixes the fast transfer of large files, which failed in its first test against a real server.

## What went wrong in 0.4.0

I dropped a file of 496 MB into a session twice.

The first time, the transfer failed at once with "Data was lost or damaged on the way. Try again." The client sends the drop and the first messages of the transfer one right after the other, and the first message of the transfer never reached the agent as a message. The logs of 0.4.0 cannot tell whether it was lost on the way or arrived damaged, because the agent dropped such data without a word.

The second time, the transfer started, and no data ever reached the agent. The client waited a full minute before it gave up with "The agent stopped answering during the transfer." Each piece of the file was sent in one call of about 700 KB to the Microsoft control, which did not report any error and did not deliver it.

## What changed

- The agent gets ready for the transfer when it offers it, at the start of the drag. Messages of the transfer that arrive early wait for the drop instead of being lost.
- The agent logs every line it drops and every transfer message it ignores. A missing first message is now named as such in the log.
- The client sends the files in pieces of 32 KiB instead of 256 KiB, so that each call to the control stays small.
- The agent confirms the first piece of every file at once. When that confirmation does not come within 10 seconds, the client stops the transfer with "The agent did not acknowledge the first data of the transfer." instead of waiting a minute. Its log then says how the data was sent.
- Both logs have a line for the first piece sent and received, which shows whether data gets through.
- When the agent does not answer the start of a drag, or a transfer, the client looks for it again. An agent that exited or restarted in the session no longer leaves the client on "Agent ready" with nobody listening.

## New setting

The size of the pieces is the setting `transferChunkBytes` in `%LOCALAPPDATA%\UltimateRDP\client.json`, 32768 bytes by default, from 4096 to 262144. You should not need to change it. If a transfer still fails at its start, a smaller value is worth a try.

## Upgrade and fallback

The client and the agent must both run 0.4.1.

If the fast transfer still fails for you, set "Fast transfer of large files" to Never in the agent tray menu, or `fastTransfer` to `never` in `agent.json`. The files are then read through drive redirection, as in 0.3.0. A transfer that fails does not switch to drive redirection by itself.

I would like to hear whether the transfer works on your connection, with both logs.
