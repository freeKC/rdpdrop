This release sends large files through the UltimateRDP channel about 2.5 times faster, and keeps the fast transfer when you release the button quickly.

## What the measurements of 0.4.4 showed

I transferred a large file with 0.4.4 on both sides and read both logs.

- The client spent 1 percent of the transfer inside its calls to the Remote Desktop control.
- The agent waited for data 55.3 s out of 56.9 s, and spent 1.3 s on what it received.
- The channel was full, at about 5.8 MB/s, while the file arrived at 2.1 MB/s.
- The agent read two bytes for every character the client sent: from the client to the agent, the control sends each character as UTF-16.

Neither side held the transfer back. The encoding did: base64 adds a third, and two bytes per character double it, so each byte of the file took 2.67 bytes on the channel.

## The denser encoding

The agent now tells the client how the data of the client reaches it. When each character arrives as two bytes, the client packs 15 bits of the file into each character, and a byte of the file takes about 1.07 bytes on the channel. On the same channel of 5.8 MB/s, I expect about 5.4 MB/s instead of 2.1 MB/s. When each character arrives as one byte, the client keeps base64. The checksums, the acknowledgements and the progress are unchanged.

The client log says which encoding a transfer uses, and both logs end the transfer with its rate, as in 0.4.4.

## Releasing the button quickly

When you release the button before the agent answered the start of the drag, the client now waits for that answer, for at most a second and a half, with "Preparing..." in the progress window. Before, the drop went out at once, and a large file then went through drive redirection at the slow rate. This was planned as 0.4.5 and ships here.

When the agent needs more than 0.7 s to check the items, it first sends a provisional answer. The agent now marks it as such, and the client waits for the final answer, which may offer the fast transfer, within the same second and a half.

## Upgrade

Install 0.5.0 on both sides. With an older agent, the 0.5.0 client still works and sends base64 as before; the denser encoding needs both sides at 0.5.0.
