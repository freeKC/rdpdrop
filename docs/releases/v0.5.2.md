This release makes the transfer of large files recover by itself when a piece of data arrives damaged in the session, as it already did when a message was lost.

## Why

On 10 November, with 0.5.1 on both sides, a transfer of 790 MB failed at its very start with "Data was lost or damaged on the way". I read the logs of both sides. The agent received the first two messages of the transfer and the beginning of the first piece of data, but the data itself could not be decoded. The same drop six seconds later went through at 2.5 MB/s, and a whole transfer of the same size had worked that morning. So the channel delivered one message damaged, once. The agent of 0.5.1 gave up on such a message instead of asking for it again.

## What the transfer does now

- A piece of data that arrives damaged is treated like a lost one: the agent leaves it, asks the client for it again, and the transfer goes on. The same limits apply, up to ten requests for the same message.
- The client sends again exactly what it sent the first time.
- Pieces sent in base64 now say their length, so that a piece that lost a block of characters on the way is seen as damaged too.
- The agent log describes each damaged piece, without its content: how many characters it had and should have had, and the first character that does not belong. Both logs count the damaged pieces in the summary of each transfer. If you see "arrived damaged" in the agent log, please send me both logs: I want to learn what this damage looks like.

## Upgrade

Install 0.5.2 on both sides. An agent 0.5.1 still fails the transfer on a damaged piece of data.
